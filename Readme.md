# Custom Thread Pool — Отчет

### Запуск
1) Сделать git clone
2) mvn clean package
3) java -cp target/Multithreaded-project-1.0-SNAPSHOT.jar org.example.Main

## 1. Архитектура пула

Реализован собственный пул потоков со следующими компонентами:

- **CustomThreadPool** — ядро, управляет Worker'ами, распределяет задачи
- **Worker** — рабочий поток с собственной очередью задач
- **CustomThreadFactory** — фабрика потоков с именованием и логированием
- **RejectedExecutionHandler** — политика отказа (AbortPolicy)
- **DefaultRejectedHandler** — отклонение задачи с исключением

### Параметры конфигурации:
| Параметр | Назначение |
|----------|------------|
| corePoolSize | Минимальное число потоков (живут всегда) |
| maxPoolSize | Максимальное число потоков |
| keepAliveTime | Время простоя лишних потоков до завершения |
| queueSize | Размер очереди каждого Worker'а |
| minSpareThreads | Минимум свободных потоков |

---

## 2. Механизм распределения задач (Round Robin)

Каждый Worker имеет **собственную очередь** задач (LinkedBlockingQueue). При поступлении задачи диспетчер пула выбирает Worker по алгоритму **Round Robin** с использованием `AtomicInteger`:

Задача 1 → Worker-1

Задача 2 → Worker-2

Задача 3 → Worker-1


Атомарный счетчик гарантирует потокобезопасность при конкурентных вызовах `execute()`.

**Преимущества подхода:**
- Нет единой точки блокировки (каждый поток работает со своей очередью)
- Простота реализации
- Равномерное распределение при однородных задачах

**Недостатки:**
- Если задача "тяжелая", её Worker занят надолго, а очередь копится, хотя другие Worker'ы могут простаивать
- Нет автоматической балансировки по загруженности

---

## 3. Политика отказа

Выбрана **AbortPolicy** — при переполнении всех очередей и достижении maxPoolSize задача отклоняется с исключением `RuntimeException`.

**Почему выбран этот подход:**
- Задача не теряется незаметно
- Вызывающий код сразу узнает о проблеме и может её обработать (retry, fallback)

**Недостатки:**
- При отсутствии обработки исключения программа крашится
- В высоконагруженных системах может потребоваться CallerRunsPolicy для естественного backpressure

---

## 4. Сравнение со стандартным ThreadPoolExecutor

| Характеристика | CustomThreadPool | ThreadPoolExecutor |
|----------------|------------------|--------------------|
| Очереди | Одна очередь на Worker | Одна общая очередь |
| Балансировка | Round Robin | Естественная (кто первый взял) |
| minSpareThreads | Есть | Нет (только corePoolSize) |
| Кастомизация | Полный контроль над кодом | Ограничена параметрами |
| Производительность | Лучше при большом числе потоков (нет блокировки на общей очереди) | Лучше при малом числе потоков (проще) |
| Стабильность | Зависит от реализации | Проверена годами |

**Вывод:** CustomThreadPool эффективнее при большом количестве потоков благодаря отсутствию конкуренции за общую очередь. Однако для большинства задач стандартный `ThreadPoolExecutor` достаточен и надёжнее.

## 5. Оптимальные параметры (мини-исследование)

### CPU-bound задачи:

- corePoolSize = N_CPU
-  maxPoolSize = N_CPU + 1
-  queueSize = 100-500
-  keepAliveTime = 60s


### IO-bound задачи:

- corePoolSize = N_CPU * 2
- maxPoolSize = N_CPU * 4
- queueSize = 500-1000
- keepAliveTime = 30s


### Смешанные задачи (рекомендация по умолчанию):

- corePoolSize = N_CPU
- maxPoolSize = N_CPU * 2
- queueSize = 200
- keepAliveTime = 60s
- minSpareThreads = 1


**Обоснование:**
- Превышение `N_CPU * 2` потоков приводит к избыточному переключению контекста
- Слишком маленькая очередь вызывает частые отказы и создание лишних потоков
- Слишком большая очередь потребляет память и увеличивает latency
- `minSpareThreads = 1` даёт компромисс между готовностью к нагрузке и расходом ресурсов

## 6. Сравнение с Tomcat/Jetty

| | CustomThreadPool | Tomcat | Jetty |
|---|------------------|--------|-------|
| Модель очереди | Одна на Worker | Одна общая | Одна общая |
| Приоритеты задач | Нет | Есть | Есть |
| minSpareThreads | Есть | Да (minSpareThreads) | Нет |
| Стабильность | Учебный проект | Production-ready | Production-ready |

**Вывод:** Tomcat и Jetty предлагают более зрелые реализации с дополнительными возможностями (приоритеты, мониторинг JMX), но архитектура с отдельными очередями в CustomThreadPool потенциально лучше масштабируется при высокой конкуренции.

---

## 7. Заключение

Реализованный пул потоков демонстрирует ключевые принципы работы thread pool:
- Переиспользование потоков
- Ограничение ресурсов (maxPoolSize, queueSize)
- Обработка перегрузок (RejectedExecutionHandler)
- Балансировка задач (Round Robin)
- Корректное завершение (shutdown/shutdownNow)

Пул пригоден для использования в качестве учебного примера и демонстрирует понимание многопоточности в Java.
